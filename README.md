# 微信群 AI 群友 · WeChat Groupmate

把一个 **DeepSeek** 驱动的 AI 变成微信群里的一个**普通群友**。它读得懂群里的话、看得懂图片、听得懂语音,被 @ 了就答,该接话的时候会主动搭一句,还会记事儿。

> **写给第一次看到这个仓库的人(包括 AI)**
> 这份 README 自包含:看完就能明白它在干什么、怎么装、怎么配、为什么这么设计。
> 如果你是一个 AI Agent 正在帮人部署,请直接跳到 [第 2 节 快速开始](#2-快速开始),
> 按顺序执行即可;**遇到问题看 [第 7 节 排错](#7-排错)**。

## 1. 它是什么

### 能力

| 能力 | 说明 |
|---|---|
| **读群消息** | 轮询微信本地数据库,白名单内所有群的消息都进上下文 |
| **被 @ 必回** | 支持自定义触发名,`@小助手 问题` 直接答问题本身 |
| **图片理解** | 自动解密下载图片 → 压缩 → 发给多模态模型(作业题、截图、表情包都能看) |
| **语音理解** | 微信语音是 SILK 格式 → 解码成 WAV → 语音识别 → 当文字处理 |
| **主动接话** | 没被 @ 也可能接:有人在问问题、或者正在接着它的话聊 |
| **长期记忆** | 从聊天里提炼事实,带时效(约好的事会过期,生日/偏好长期保留) |
| **限流护栏** | 每分钟/小时/天三级上限,连续失败自动暂停,有紧急停止开关 |

### 它怎么"看"到微信

```
微信客户端 (Windows)
   │
   ├─ 消息 ──→ 本地加密 SQLite (db_storage/) ──解密──→ 轮询读取
   ├─ 图片 ──→ media_*.db (aeskey 加密) ──解密──→ 落盘 → 压缩 → 多模态模型
   └─ 语音 ──→ media_*.db (SILK 格式) ──pysilk解码──→ WAV → 语音识别
                                                    │
   发送 ──→ UI 自动化(UIA 控件树)点开群 → 输入 → 发送
```

**关键点:全部是"读本地文件 + 点界面",没有注入微信进程、没有 hook、没有改微信。**

### 它不做什么

- ❌ 不破解微信、不注入 DLL、不 hook 内存
- ❌ 不发朋友圈、不加好友、不群发
- ❌ 不自动通过好友申请
- ❌ 不会"完全不被发现"——**UI 自动化本身是有风险的,见 [第 6 节](#6-已知约束与坑)**

## 2. 快速开始

> 下面这一节就是**安装与部署**的完整流程。
> 想要更细的逐步操作(含每一步的预期输出),看 **[INSTALL.md](INSTALL.md)**。

### 2.1 环境要求

| 项目 | 要求 |
|---|---|
| 系统 | **Windows 10 / 11**(必须,依赖 Windows 的 UI 自动化和注册表) |
| Python | **3.10+**(代码用了 `X \| Y` 类型语法) |
| 微信 | **Windows 版微信 4.x**,已登录并保持窗口存在 |
| 算力 | 不需要 GPU(推理全在云端 API) |

> **强烈建议在虚拟机里跑**(见 [2.5](#25-强烈建议用虚拟机))。
> 虚拟机配置:2 核 / 4 GB 内存 / 50 GB 磁盘就够,不需要显卡。

### 2.2 装依赖

```bash
# 1) 建虚拟环境(推荐,避免污染系统 Python)
python -m venv .venv
.venv\Scripts\activate

# 2) 装依赖
pip install -r requirements.txt
```

`requirements.txt` 里的核心是 **`wechatauto-replica`** —— 它提供微信的读写通道
(读数据库、下载图片/语音、UIA 发送)。**本项目不含它的代码,只调用它的公开 API。**

### 2.3 拿两个 API Key

| Key | 用途 | 去哪拿 | 花钱吗 |
|---|---|---|---|
| `DEEPSEEK_API_KEY` | 生成回复、看图、提炼记忆 | https://platform.deepseek.com | 便宜,按量计费 |
| `ASR_API_KEY` | 语音转文字 | https://cloud.siliconflow.cn | 有免费额度 |

**语音识别是可选的** —— 不配也能跑,只是听不了语音(而且它会如实告诉群里"听不了")。
任何 **OpenAI 兼容的 `/audio/transcriptions` 接口**都行,不限于 SiliconFlow。

设置环境变量(**推荐,不要写进配置文件**):

```powershell
# 当前会话
$env:DEEPSEEK_API_KEY = "sk-你的key"
$env:ASR_API_KEY = "sk-你的key"

# 永久(写入用户环境变量,重开终端生效)
[Environment]::SetEnvironmentVariable("DEEPSEEK_API_KEY", "sk-你的key", "User")
[Environment]::SetEnvironmentVariable("ASR_API_KEY", "sk-你的key", "User")
```

> **为什么要读注册表**:Windows 上"设了环境变量但当前进程读不到"非常常见
> (进程从旧会话启动,没继承新变量)。本项目读 Key 的顺序是
> **显式配置 → 进程环境变量 → `HKCU\Environment` 注册表**,
> 三层兜底,避免出现"明明配了却说没配"。

### 2.4 配置

```bash
copy config.example.json config.json
```

然后改 `config.json` 里**至少这三处**:

```jsonc
{
  "dry_run": true,                              // 先保持 true!只打印不发
  "wechat_account": "",                         // 留空=自动检测。多账号机器必填
  "trigger": {
    "groups": ["你的群名"],                     // 群名必须和微信里显示的一字不差
    "mention_names": ["小助手"]                 // 群里 @ 它时用的名字
  }
}
```

### 2.5 强烈建议用虚拟机

**UI 自动化操作微信有被风控的风险。** 建议:

1. 装 **VirtualBox**(免费),新建 Windows 10 虚拟机,2 核 / 4 GB / 50 GB
2. 虚拟机里装微信,**登录一个专门的小号**(不要用主号)
3. 把本项目拷进虚拟机运行

这样即使出问题,影响的也只是小号。

> 如果只有一个号,至少**把 `guard` 里的限流调保守**(见 [3.3](#33-guard--护栏))。

### 2.6 先体检,再演示,最后才真跑

```bash
# ① 体检:检查 Python、依赖、微信进程、配置
python run_bot.py check

# ② 演示:不连微信,用假数据跑一遍完整决策流程,看它会不会乱说话
python run_bot.py demo

# ③ 真跑(dry_run 还是 true,只打印不发送)
python run_bot.py run

# ④ 确认日志里的回复都正常后,把 config.json 的 dry_run 改成 false
#    再跑一次,这才真的会发消息
python run_bot.py run
```

**务必按 ①→④ 的顺序。** 直接跳到 ④ 很容易在群里刷屏。

### 2.7 跑起来之后

- 日志默认写到 `bot.log`,也可以直接看终端输出
- 在群里发 `@小助手 你好` 试试
- **紧急停止**:在项目根目录建一个名为 `STOP` 的文件,机器人立刻停止回复

```bash
echo. > STOP      # 停止
del STOP          # 恢复
```

## 3. 配置详解

`config.json` 分成 6 段。下面只讲**需要你动**的。

### 3.1 `trigger` — 什么时候回

```jsonc
{
  "groups": ["群A", "群B"],       // 白名单。不在名单里的群,消息读都不读
  "mention_names": ["小助手"],     // @ 这些名字就触发
  "keywords": [],                 // 关键词触发(可选,留空就只认 @)
  "quiet_hours": [1, 7],          // 1点到7点不主动说话(@ 仍然会回)
  "max_reply_chars": 600          // 单条回复字数上限
}
```

**触发优先级**:`@` > 图片跟进 > 语音跟进 > 关键词 > 主动接话。
**`@` 会绕过所有冷却** —— 因为要求是"连续两个 @ 都必须答,不能遗漏"。

几个容易踩的参数:

| 参数 | 默认 | 说明 |
|---|---|---|
| `proactive_enabled` | `true` | 没被 @ 也可能主动接话。**话痨就设 false** |
| `proactive_cooldown_seconds` | `20` | 主动接话的冷却。**嫌吵就调大** |
| `mention_debounce_seconds` | `0` | `@` 的防抖。`0` = 不防抖,连着 @ 就连续答 |
| `image_wait_seconds` | `3` | 收到 @ 后等几秒,看有没有补发文字/图片 |
| `image_lookback_seconds` | `600` | 往前找多久内的图片。有人先发图过一会儿才 @,窗口太小会漏 |

### 3.2 `llm` — 用哪个模型

```jsonc
{
  "base_url": "https://api.deepseek.com/v1",   // OpenAI 兼容接口即可
  "model": "deepseek-chat",
  "temperature": 1.3,                          // 高一点更像真人,低一点更稳
  "max_tokens": 1200,
  "history_limit": 30                          // 每次带多少条上下文给模型
}
```

### 3.3 `guard` — 护栏

**这是防止被封的关键。** 默认值已经很保守:

```jsonc
{
  "max_per_minute": 12,           // 每分钟最多发 12 条
  "max_per_hour": 150,
  "max_per_day": 800,
  "max_consecutive_failures": 5,  // 连续失败 5 次自动暂停
  "kill_switch_file": "STOP"      // 建这个文件立刻停
}
```

**如果你的号比较重要,建议把 `max_per_minute` 降到 4~6。**

### 3.4 `voice` — 语音识别

```jsonc
{
  "enabled": true,
  "base_url": "https://api.siliconflow.cn/v1",
  "model": "FunAudioLLM/SenseVoiceSmall",   // 免费且中文准确率很高
  "language": "zh",
  "max_seconds": 120,                        // 超过这个长度的语音不处理
  "tell_when_unavailable": true              // 听不了时如实说一声,别装死
}
```

> **换成别家的语音识别**:任何实现 `POST /audio/transcriptions`
> (multipart 上传 `file`,返回 `{"text": "..."}`)的服务都能直接换 `base_url` + `model`。

### 3.5 `persona` — 人设

见 [第 4 节](#4-人设怎么写才像人)。

### 3.6 顶层

```jsonc
{
  "dry_run": true,               // true=只打印不发送。第一次务必保持 true
  "wechat_account": "",          // 账号目录名。多账号机器必填,否则可能读到没登录的那个
  "log_file": "bot.log",
  "learn_every_messages": 25     // 每 25 条消息提炼一次长期记忆
}
```

## 4. 人设怎么写才像人

`persona` 是**七字段结构**,不是笼统一句"你是个开朗的人"。

这个结构来自 [PersonaMorph](https://github.com/Eifptaur/Eif-MAPT-PersonaMorph) 的实测结论:

> 只写性格,模型演的是**标签**;写清**动机**,它才演得出**人**。
> 补齐「动机」字段后,角色决策准确率 **62.9% → 95.5%**。

| 字段 | 作用 | 写不好会怎样 |
|---|---|---|
| `background` | 身份、处境 | 泛泛而谈 → 说话没有具体感 |
| `personality` | 性格 | 只写形容词 → 演标签 |
| **`motivation`** | **它想要什么** | **缺这个最致命,角色立不起来** |
| `values` | 在乎什么、不做什麼 | 容易说违心话 |
| `language_style` | 怎么说话 | 容易变成客服腔 |
| `behavior_rules` | 行为细则 | 容易一次发一大段 |
| `limitations` | 不懂什么 | 容易瞎编 |
| `examples` | 几段示例对话 | 语气跑偏 |

**`examples` 特别重要** —— 三段真实对话胜过十句"请用轻松的语气说话"。

留空的字段会**自动跳过**,不强迫一次填完。

## 5. 架构与设计决策

### 5.1 模块

```
groupmate/
  config.py       配置:dataclass + 三级 Key 兜底(显式 → 环境变量 → 注册表)
  message.py      消息模型 + @ 解析 + 历史拼接(与微信实现解耦,可离线测试)
  policy.py       决策引擎:要不要回这条?(触发/冷却/静默/限流)
  proactive.py    主动接话判断(规则级 + 可选模型级)
  bot.py          主循环:轮询 → 决策 → 生成 → 发送 → 记账
  llm.py          大模型调用(文本/视觉/记忆提炼/输出清洗)
  memory.py       长期记忆:事实提取、时效、相关性检索、落盘
  voice.py        语音:SILK → WAV → 在线识别(带磁盘缓存)
  wx_backend.py   微信接入:数据库读取、媒体下载、UIA 发送
  backend.py      后端接口 + 测试桩(MockBackend)
run_bot.py        命令行入口(check / demo / run)
test_policy.py    测试套件(206 项,不需要微信和网络)
```

**分层的关键**:`policy` / `proactive` / `memory` / `message` **完全不依赖微信**,
所以能用 `MockBackend` 离线测 206 项,不需要真微信、不花钱、毫秒级跑完。

### 5.2 决策流程

```
消息到达
  │
  ├─ 是机器人自己发的? ──→ 丢弃(防自问自答)
  ├─ 群不在白名单? ──────→ 丢弃
  ├─ 空消息? ────────────→ 丢弃(图片/语音除外)
  ├─ 深夜静默时段? ──────→ 丢弃(@ 除外)
  │
  ├─ 触发判定(按优先级)
  │    @ 我? ─────────────→ 触发
  │    刚 @ 过我的人发图/语音? → 触发(同一次交互的延续)
  │    命中关键词? ────────→ 触发
  │    像在问问题/接着我的话? → 主动接话(受冷却限制)
  │
  ├─ 冷却检查 ──→ @ 和跟进完全绕过;其它受 per-user / per-group 冷却
  ├─ 硬护栏 ────→ 每分钟/小时/天上限 + 连续失败熔断
  │
  └─ 通过 → 组装问题(正文 + 补发内容 + 语音识别结果)
            + 图片 → 调模型 → 清洗输出 → 发送 → 记账
```

### 5.3 为什么这么设计(踩过的坑)

这些都是**实际调试出来的**,不是拍脑袋:

| 设计 | 为什么 |
|---|---|
| **时间基准用"单调消息游标"** | 机器人追赶积压消息时,消息时间戳落后真实时钟。若拿 `time.time()` 当基准,`现在 - 上次回复` 会变成**负数**,老消息被误判成"刚回过"而**静默丢掉** —— 表现就是"@ 了有时候不回"。游标取"已见消息时间戳的高水位",只增不减。 |
| **语音有"补试队列"** | 微信是**延迟下载**语音的:语音条立刻显示,但音频要 **30~60 秒**后才写进 `media.db`。一次取不到就放弃 = "有时能识别有时不能"。所以拿不到就排队,之后每轮重试,拿到就补一句。 |
| **图片下载带重试 + 数据库兜底** | 微信稍后才把图片写进本地库;而且机器人重启后水位跳到最新,之前发的图会被当历史跳过。所以除了重试,还会直接查库补捞最近的图。 |
| **回声拦截必须用真实时钟** | 拦截"自己发的消息被读回来"。若用消息时间戳比对真实时钟,追赶积压时窗口判断失效 → **自己触发自己,连发好几条**。 |
| **回声前缀判定要双向限长** | 机器人回了个"好的",180 秒内有人发"好的 那我明天再问你"会被误判成自己的回声 —— 而拦截发生在存上下文**之前**,这条真人消息会**彻底消失**。所以短消息只认完全相等。 |
| **`: @` 匹配要带边界** | 纯子串判断会让 `@小助手bot` 这种"别人昵称以机器人名开头"的情况**误唤醒**,白烧一次模型调用。 |
| **语音识别结果必须参与触发判定** | 语音消息的正文是 `[语音]` 占位符,真正的话在另一个字段。只读正文的话,"用语音 @ 我"完全判不出来,整套语音功能形同虚设。 |
| **等待补发窗口取到的消息不能丢** | 等待期间会再 poll 一次,而 poll 是"取走即清空"。这些消息既不在本轮队列里,又不在下一轮 —— 直接消失。所以有独立的待处理队列。 |
| **消息去重键要带分片** | 微信的 `local_id` **只在单个分片内唯一**,跨分片会重复。只用 `群|local_id` 会把两条不同消息判成重复,第二条永远不回。 |
| **配置读取失败不能清空记忆** | 记忆文件里有一条坏数据就整份清空,再一保存就把用户的记忆**永久抹掉**。所以逐条解析、坏条目跳过,解析失败时**拒绝写入**。 |

### 5.4 输出清洗

模型输出的文本会经过:

1. **表情数量限制** —— 最多 1 个,多了会像刷屏
2. **长度截断** —— 按 `max_reply_chars`
3. **多行合并** —— 短回复被折成多行会显得像在发小作文,自动压成一行
4. **先限表情再截断** —— 否则可能把 `[捂脸]` 截成半个 `[捂`

## 6. 已知约束与坑

### 风险

| 风险 | 说明 | 怎么降低 |
|---|---|---|
| **账号风控** | UI 自动化操作微信**不是官方接口**,行为异常可能被限制 | 用**小号**、放**虚拟机**、限流调保守 |
| **消息读取依赖本地数据库** | 微信版本更新可能改库结构 | 固定微信版本,别自动更新 |
| **锁屏/切后台会发送失败** | UI 自动化需要窗口可用 | 虚拟机里保持桌面会话活跃 |
| **API 花钱** | 每次回复都调模型 | 配限流;`dry_run` 先验证 |

### 平台限制

- **只能 Windows** —— 依赖 Windows UI 自动化和注册表
- **微信必须 4.x** —— 3.x 的库结构不同
- **需要保持登录** —— 微信退出了就读不到消息

### 隐私提醒

- ⚠️ **群里的消息会被发给你配的大模型 API**(DeepSeek)。这不是本地推理。
  介意的话:换个群、或者用本地模型(把 `llm.base_url` 指向本地 OpenAI 兼容服务)
- ⚠️ **`config.json` 不要提交到 Git**(仓库已配 `.gitignore` 忽略它)
- ⚠️ **API Key 用环境变量**,别写进配置文件

## 7. 排错

### 先跑体检

```bash
python run_bot.py check
```

它会检查 Python 版本、依赖、微信进程、配置文件,并给出具体建议。

### 常见症状

| 症状 | 原因 | 解决 |
|---|---|---|
| `没有 API Key` | 环境变量没读到 | 用注册表方式设置(见 [2.3](#23-拿两个-api-key));或临时写进 `config.json` 的 `llm.api_key` |
| **一个群的消息都读不到** | 群名和微信里显示的不一致 | 看启动日志里"本机群名: ..."那行,复制准确的群名 |
| `图片通道不可用` | `wechatauto-replica` 没装好或版本太老 | `pip install -U wechatauto-replica` |
| **能读出消息但发不出去** | 微信不在前台 / 锁屏 / 会话打不开 | 保持微信窗口存在;虚拟机里别锁屏 |
| **语音识别不了** | 音频还没下载完(最常见) | 已内置补试队列,等 30~60 秒会自动补答。若一直不行,看日志里的"原因=" |
| **它自己跟自己说话** | 回声拦截失效 | 已修(双向限长)。若复现,看日志里是不是 `读取 [群] <自己的话>` |
| `运行了但永远不回` | 数据库没就绪或群没映射上 | 日志里找 `读消息能力未就绪` |
| **回复很慢** | 首次调模型要建连 | 正常。图片/语音会额外多花几秒下载 |

### 看日志

日志格式是 `[时间] 事件`。关键行:

```
读取 [群名] 消息内容           ← 收到并判定要处理
已获取语音(3.1 KB): xxx.silk   ← 语音音频拿到了
语音转文字(2.1 秒音频, 0.5s): 「...」  ← 识别成功
合并后的问题:「...」| 图片 2 张   ← 最终要问模型的内容
[已发送] 「群名」(mention触发): ...  ← 真的发出去了
```

**如果只有"读取"没有"[已发送]",说明被冷却/护栏挡住了,日志会写明原因。**

## 8. 常见问题

**Q:会被封号吗?**
A:UI 自动化有风险,但比"协议逆向/注入"低得多 —— 因为它就是**模拟人在点界面**。
仍然建议:**用小号 + 虚拟机 + 保守限流**。

**Q:能同时管多个群吗?**
A:能。`trigger.groups` 填多个群名即可,限流是全局的。

**Q:能用别的模型吗(Claude/GPT/本地)?**
A:能。任何 **OpenAI 兼容**的 `/chat/completions` 接口都行,改 `llm.base_url` + `model` 即可。
图片理解需要模型支持视觉。

**Q:能不用云 API,全本地跑吗?**
A:可以,但要把 `llm.base_url` 指向本地的 OpenAI 兼容服务(如 Ollama / vLLM)。
语音识别同理。**本仓库不含本地推理引擎。**

**Q:为什么不用 Hook / 协议逆向?**
A:因为**更危险也更容易失效**。改微信进程内存、破解通信协议,既违反用户协议,
每次微信更新都会挂,而且有明显法律风险。UI 自动化是"最笨但最稳"的路子。

**Q:消息存在哪?**
A:记忆落盘在 `memory.json`,图片/语音缓存在 `_images/` `_voices/`(自动清理旧的)。
`config.json` 和这些运行时文件都在 `.gitignore` 里。


### 测试隔离(改代码时请注意)

测试和演示**不允许**在仓库里留下任何文件。已经做了两层隔离:

1. `GroupMateBot(cfg, backend, llm=..., data_dir=<临时目录>)`
   —— 记忆(`memory.json`)和运行状态(`bot_state.json`)都写到 `data_dir`
2. `WxBackend.media_cache_dir = <临时目录>`
   —— 图片/语音缓存(`_images` / `_voices`)不再落在仓库根

> ⚠️ 踩过的坑:某些受限环境里 `tempfile.gettempdir()` 会**指向当前工作目录**,
> 于是 `tempfile.mkdtemp()` 把临时目录直接建在仓库里。
> 所以 `test_policy.py` 开头包装了一次 `tempfile.mkdtemp`,统一登记 + 退出时清理。
> **新写的测试请用文件里已有的 `tempfile`,不要另外 import 一份。**

### 加新功能

- **只改决策规则** → 动 `policy.py` / `proactive.py`,然后在 `test_policy.py` 里补用例
- **改模型调用** → 动 `llm.py`,注意 `reply()` 的签名要和桩保持一致
- **加新的微信能力** → 动 `wx_backend.py`,新方法要在 `backend.py` 的 `Backend` 里声明
- **别在 `policy` / `memory` / `message` 里 import 微信相关的库** —— 这三个模块要能脱离微信独立测试
